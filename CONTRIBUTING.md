# Contributing to Concerto

Thanks for your interest in contributing. Concerto is MIT-licensed and we want it to stay easy to fork, audit, and self-host. The rules below exist to keep that promise.

## TL;DR

- Sign off your commits with `git commit -s` (Developer Certificate of Origin).
- Don't introduce GPL, AGPL, LGPL, SSPL, or BSL dependencies — CI will fail.
- New runtime-extensible behavior should land behind a trait, not a hardcoded provider.
- Don't add phone-home telemetry, license checks, or account requirements to the Core.
- Security issues: email security@concerto.app — don't file a public issue.

## Developer Certificate of Origin (DCO)

We use the Linux kernel's [DCO](https://developercertificate.org/) model instead of a CLA. Every commit must be signed off:

```
git commit -s -m "your commit message"
```

This adds a `Signed-off-by: Your Name <your@email>` trailer. By doing so, you confirm that the contribution is yours to give and that it can be redistributed under the project's license (MIT).

**Why DCO and not a CLA?** A CLA would let Concerto Inc unilaterally relicense your contributions (for example, to a more restrictive license later). DCO doesn't. This is intentional: the MIT codebase stays MIT, by design. If you'd like more detail, see `design/18_Distribution_and_Operations.md` §3.6.

## Project structure

The repo is a Cargo workspace plus a JS/Tauri client tree. See `design/00_Architecture_Overview.md` §6.1 for crate organization. The full 17-sub-system design lives in `design/`; start with `00_Architecture_Overview.md`.

## Coding standards

- **Rust:** stable toolchain pinned in `rust-toolchain.toml`. `cargo fmt` and `cargo clippy -- -D warnings` are gated in CI.
- **JS / TS:** Prettier + ESLint configs live in the relevant client trees. Run `pnpm lint` before pushing.
- **Tests:** Every PR adds or updates tests unless the change is a no-functional docs change. New sub-system features should include unit tests at minimum; trait seams (per `18 §3.7`) should include a fixture impl to keep the contract testable.

## License compliance

CI enforces:

- All new Rust dependencies must be MIT, Apache-2.0, BSD-2/3, ISC, 0BSD, Unicode-DFS-2016, or Zlib. `cargo deny` will fail the build otherwise.
- All new JS dependencies must satisfy the same allow-list. A script in `.github/workflows/licenses.yml` checks `pnpm licenses list --json`.
- `THIRD_PARTY_LICENSES.md` is regenerated by CI on release tags. Don't hand-edit it.

If you have a genuine need for a dependency outside the allow-list, open an issue first; we'll look for alternatives. Re-licensing a transitive dep is harder than picking a different one upfront.

## What not to add

Concerto's local-first / no-accounts / E2EE story depends on the *absence* of certain code paths. PRs that add any of the following will be sent back with reasons:

- License checks, entitlement validation, or feature-gating against a server.
- Phone-home telemetry, analytics, crash reporting that egresses by default.
- Account creation, email collection, or third-party SSO requirements for the Core.
- Hard dependencies on a Concerto-Inc-operated service (the relay is OK *because* it's also self-hostable; an analytics service would not be).
- Closed-source or proprietary blobs.

The Core never collects PII without explicit opt-in. See `design/09_Persistence.md` §3.6 for the full PII inventory.

## Architecture decisions

If your change touches a locked decision in `design/00_Architecture_Overview.md` §6, the PR should update §6 first (and explain why), then propagate through the affected sub-system docs. Big architectural changes deserve a proposal issue before code.

Extension trait seams (the V2.0 enterprise-module pattern in `design/18_Distribution_and_Operations.md` §3.7) are a contract: don't add hardcoded providers where a trait already exists. If you're tempted to fork a sub-system to handle a new backend, propose adding it as an additional impl behind the trait instead.

## Security

Report vulnerabilities privately to security@concerto.app. PGP key fingerprint and disclosure SLA are in `SECURITY.md`. Don't open public issues for security problems — it puts users at risk before a fix is available.

## Self-hosting

If you're building Concerto to run your own deployment (your own relay, your own mobile builds, your own update server), the steps live in `design/18_Distribution_and_Operations.md` §3.2 ("Self-host parity guarantee"). We treat any regression in self-host parity as a P1 bug — please file it.

## Trademark

"Concerto" is a registered trademark. You can use the name to factually describe interoperability ("works with Concerto") but not as the name of a fork or competing product. Full guidance in `TRADEMARKS.md`.
