## Goal
Close the loop on `design/13 R-9`: when a workarea's coordinated PR-set merge completes, transition the linked Linear/Jira issue's status (e.g. *In Progress → Done*) — **per-project opt-in**, reusing Task 317's `write_back` trait seam and the shared `concerto-vcs/testkit` doubles. Today Task 317 ships Linear/Jira issue **fetch** plus a *no-op* `write_back` seam (a deliberate stub, per `PHASE3_PLANNING §1 D5`), and Task 320 emits a `pr_set.merged` / `MergeProgress::SetMerged` completion signal — but nothing connects them: a merged PR set leaves the tracker issue untouched. This task hangs an issue-write-back step off 320's coordinated-merge completion: on `SetMerged`, if the project has opted in (`projects.settings_json.issue_write_back`) and the workarea's originating issue is resolvable, call `IssueWriteBack::transition_on_merge(issue_ref, IssueTransition::MergedDone)` (317's seam, now given a real Linear/Jira implementation). The opt-in lives in `projects.settings_json` (a JSON key — **no migration**). After this task a team that turned write-back on sees their Linear/Jira issue auto-transition the moment Concerto finishes merging the workarea's PR set; teams that did not opt in see no tracker mutation. The real round-trip against live Linear/Jira is the Phase-3 Tier-3 checklist line ("fetch a real Linear and Jira issue" extends to "transition one").

## Scope — in
- **The real `write_back` implementation (in `crates/vcs`, behind 317's seam):**
  - Implement `IssueWriteBack::transition_on_merge` (317's frozen seam) for the Linear client (GraphQL `issueUpdate` mutation moving the issue to its team's "Done"/"Merged" workflow state) and the Jira client (REST `POST /issue/{key}/transitions`), replacing 317's no-op. Resolve the target state by the `IssueTransition` enum (V1.0 ships `MergedDone`; the enum is extensible). Tokens come from the keychain via 317's `VcsSecretSlot` accessors — mint nothing.
  - Dispatch GitHub-issue refs to a **no-op** (GitHub "issues" close via PR keywords, not a tracker transition — out of scope; record `Skipped`).
- **The merge-completion hook (`crates/core/src/workspace_manager/workarea.rs`):**
  - At the end of `merge_workarea_pr_set`'s success path (after `SetMerged`), read the project's opt-in (`projects.settings_json.issue_write_back`, default **off**). If on, resolve the workarea's originating issue ref (the persisted creation-time issue id — see Inputs/Implementation notes); if resolvable, call `IssueWriteBack::transition_on_merge(issue_ref, IssueTransition::MergedDone)`.
  - **Write-back never fails the merge.** A write-back error (auth lapsed, issue moved, rate-limited, ref unresolvable) is logged + audit-logged + surfaced as an informational event; the merge stays "merged." Emit a `pr_set.issue_write_back` informational broadcast event (`{workarea_id, issue_ref, outcome ∈ written|skipped|failed, detail}`) — reuse the `WorkareaEvent`/`pr_set.events` opaque-payload channel 320 added; do **not** add a new `Event` oneof arm.
- **The opt-in surface (`crates/persist/src/projects.rs` consumer side):** read `projects.settings_json.issue_write_back` (a `bool`, default false). No new column; no migration. (The Desktop toggle for it is a later UI concern — out of scope here; this task only reads the key.)
- **Tests (Tier 2, against `concerto-vcs/testkit`):** opt-in on + a Linear issue ref + a successful merge → `FakeLinear` records the `issueUpdate` to Done; same for Jira → `FakeJira` records the transition; opt-in **off** → no tracker mutation; write-back failure (fake returns an error) → merge still reported merged + a `failed` write-back event emitted (the merge result is unchanged); unresolvable/absent issue ref → `skipped`, no error; GitHub issue ref → `skipped`.

## Implementation notes
- **Reuse, don't reinvent.** The whole point of `D5` is that 317 already built the clients + the seam + the keychain creds + the `testkit` doubles. 320.5 supplies the *real `write_back` body* (Linear GraphQL `issueUpdate` / Jira `POST transitions`) and the *trigger* (the merge-completion hook). If 317's seam already has a partial impl, fill it in; do not add a parallel client.
- **The originating issue ref is the one genuinely new seam.** A workarea created from an issue (`design/03 §7.1` / Task 411 in P4) must have recorded *which* issue. Verify where that lives. If it is **not** persisted on `main` yet (likely — 411 is P4), define it minimally: a `workareas.settings_json.source_issue_ref` key (the issue URL/id captured at creation) — read it here, and **freeze that key name** so 411 writes it. State plainly in Handoff that until 411 wires the creation-time capture, the ref is only present for workareas created with it set; the test sets it directly. Do **not** invent a migration for this — it is a `settings_json` key.
- **Best-effort is a hard contract.** Wrap the entire write-back in a `let _ = ...`-style guard that converts any error into the `failed` event + an audit entry. A tracker outage must never turn a successful merge into a failed RPC. This mirrors how the smoke-critical paths swallow `git maintenance start` failures.
- **In-loop call vs. event subscription.** Prefer calling write-back **inline** at the end of `merge_workarea_pr_set`'s success path (deterministic ordering, easy to test, and the `WorkareaManager` already holds `persistence` + can hold the `IssueWriteBack` handle via a `with_vcs`-style builder). Subscribing to `PrSetMerged` from a separate task is also valid but harder to test deterministically — pick inline and note it.
- **Token hygiene.** Reuse 317's keychain accessors; never log tokens or issue bodies (mirror `gh_cli.rs`'s never-log-subprocess-output discipline and 317's no-persist-issue-body floor).
- **The Tier-2 double.** `concerto-vcs/testkit`'s `FakeLinear`/`FakeJira` (313/`D2`) record the mutation so the test asserts the right transition was sent. It does **NOT** cover a real Linear/Jira workflow-state lookup (team-specific "Done" state ids), real OAuth-token refresh mid-write, or real API error shapes → Tier-3 Phase-3 checklist ("transition a real Linear and Jira issue on merge").
- **Cross-platform:** pure Core/`crates/vcs` logic over the existing `reqwest` (rustls) dep; builds on the Windows/Linux CI lanes (Task 113).
- Regen: this task adds **no proto** (the event is an opaque payload on 320's subject) — but if any `docs/interfaces/rust-api.md`-visible public type changes in `crates/vcs`, run `./scripts/regen-interfaces.sh` and commit.
