## Goal
Pin down — in the canonical design — the exact relay→Core inbound-webhook **framing** before Task 315 implements it, so a fresh agent on 315 builds against a frozen contract instead of inventing one. `design/13 §3.2`/§6.2 says GitHub posts to a `/webhook/github/<endpoint_id>` URL on the relay and "the relay forwards the webhook payload to the Core over the existing Iroh tunnel," but it never specifies the wire shape, and `design/11` has **no inbound-HTTP-ingress concept at all** — its relay only does Iroh routing + the `/wss/<endpoint_id>` browser bridge (§3.4). The transport's channel-tag demux (`crates/transport/src/channels.rs`) is frozen at three tags (`0x01 Api`, `0x02 PushHint`, `0x03 Pairing`); there is no channel for an unauthenticated relay-originated webhook. This task amends `design/11` and `design/13` **in place** (dated-amendment style, exactly as Task 200 reconciled the adapter decision) to: (a) reserve a **fourth channel tag `0x04 Webhook`** on the frozen demux; (b) specify the **second relay HTTP route** `POST /webhook/github/<endpoint_id>` alongside the WSS bridge; (c) define the **relay→Core webhook envelope** (delivery-id, the two GitHub signature/delivery headers passed through, the opaque body) the relay pumps over an ephemeral `0x04` Iroh bidi; and (d) lock the **offline-Core behavior** (relay drops + logs, no buffering — the relay stays near-stateless per `design/11 §3.2`). This is the only Phase-3 task permitted to edit `design/`. It runs **before** 315, exactly as Task 200 ran before 201.

## Scope — in
- **Amend `design/11`** in place (dated-amendment voice, matching Task 200's merged style — an in-place correction plus a labeled `**V1.0 amendment (2026-06-05) — …**` line):
  - In §3.3 (three logical channels): add the **fourth channel** — `0x04 Webhook`, a short-lived relay-originated stream carrying one inbound webhook envelope. State that unlike `0x01`/`0x02` it does **not** establish Noise IK (no device cert is involved — the sender is GitHub via the relay, not a paired device); its authenticity floor is the per-repo HMAC the Core verifies (citing `design/13 §3.2`). State the demux byte is `0x04` and that `crates/transport/src/channels.rs` / `ChannelTag` add the arm (Task 315).
  - In §3.2 (the relay's minimal job list): add a 5th bullet — **inbound webhook forwarding**: accept `POST /webhook/github/<endpoint_id>`, open an ephemeral `0x04` bidi to the addressed Core's `endpoint_id`, write the webhook envelope, await the Core's 200/4xx ack, relay it back to GitHub. Note the relay still holds **no business state** (no buffering, no secret).
  - In §3.4 (or a new §3.4.1 next to the WSS bridge): describe the **second relay HTTP route** as a sibling of the WSS bridge — same `RelayMode::Custom` Iroh client endpoint, same parse-`<endpoint_id>`-before-work discipline, but **plain HTTPS POST → one Iroh bidi → 200 chain-back**, not a WebSocket upgrade + bidirectional pump. State the route reuses 215's relay-forced client `Endpoint`.
  - In §3.9 (ciphertext/metadata invariant): add a precise carve-out row/paragraph — the webhook body is **not** Noise-encrypted (it is GitHub's signed JSON forwarded opaquely); the relay sees the body bytes in transit (it is a transparent forwarder, exactly as for any TCP proxy) but **never the per-repo HMAC secret** (which lives only in the Core keychain) and does **no** verification, parsing, or persistence. The end-to-end authenticity guarantee is the Core-verified HMAC, not relay trust. Make explicit that this is a deliberate, bounded exception to the "relay sees ciphertext only" property and why it is safe (HMAC over the body + delivery-id idempotency at the Core).
  - In §6.2 (relay-side mermaid / prose): add the `/webhook/github/<endpoint_id>` route node feeding an ephemeral Iroh bidi to the Core (sibling of the `Wss` node).
- **Amend `design/13`** in place (same dated-amendment voice):
  - In §3.2: replace the vague "forwards the webhook payload to the Core over the existing Iroh tunnel" with the precise framing — the relay opens an **ephemeral `0x04` Webhook bidi** (not the "existing" long-lived API tunnel; there may be no live device session when a webhook lands), writes the **`WebhookEnvelope`** (defined below), and chains the Core's status back to GitHub. Cite `design/11 §3.4.1`.
  - In §6.2: annotate the sequence diagram's `Relay→Trans` arrow with the envelope + the `0x04` channel; annotate the `Vcs-->>Trans: 200 OK to GH (chained back)` arrow as the ack the relay relays back over the same bidi.
  - In §8: confirm the **offline-Core** failure row — if the relay's dial to `endpoint_id` fails (no route / Core down), the relay returns a `502`/`503` to GitHub (GitHub retries per its own redelivery policy) and **drops + logs** the attempt; it does **not** buffer (per `design/11 §3.2` near-stateless). Add this as an explicit row if absent.
- **Define + FREEZE the `WebhookEnvelope` framing** in the `design/11 §3.4.1` amendment (the contract 315's relay-write side and Core-read side both implement): a length-delimited frame on the `0x04` bidi carrying:
  1. `delivery_id` — the GitHub `X-GitHub-Delivery` header value (UUID string), the idempotency key 315's `webhook_deliveries` cache (migration 0013) dedupes on.
  2. `signature_256` — the `X-Hub-Signature-256` header value (`sha256=<hex>`) passed through verbatim; the Core recomputes HMAC-SHA256 over `body` with the per-repo `VcsSecretSlot::WebhookSecret` and constant-time-compares.
  3. `event_type` — the `X-GitHub-Event` header (`pull_request`/`check_run`/`deployment`/`pull_request_review_thread`/…) so the Core can route the parse without sniffing the body.
  4. `endpoint_id` — the addressed Core endpoint id from the path (redundant with the dial target but carried so the Core can assert it matches its own identity / reject a misrouted frame).
  5. `body` — the raw GitHub POST body bytes, **opaque** to the relay, HMAC-verified at the Core. Bounded to GitHub's documented max delivery size (state the ceiling, e.g. 25 MiB, well under the transport's 64 MiB `MAX_MESSAGE_SIZE`).
  State the **concrete encoding** to FREEZE (recommend: a minimal length-prefixed framing — `u32` body length + the four header strings as length-prefixed UTF-8 — OR a single deterministic-CBOR map; pick one and pin it so 315 has no choice to make). State the Core's **ack frame**: a single status byte / small reply the relay maps to the HTTP status it returns to GitHub (`200` accepted, `4xx` HMAC/parse reject, `5xx` Core error).

- **Match Task 200's dated-amendment voice exactly.** Read the merged `design/11 §3.1.1` Task 200 wrote (the "V1.0 amendment (2026-06-02)" block) for the house style: an in-place clarification + a labeled dated line citing the source decision. - **Prefer one new subsection over scattering edits.** As Task 200 created `design/11 §3.1.1` to host its amendment + gotchas, create **`design/11 §3.4.1` — "Inbound webhook forwarding (relay→Core, `0x04` channel)"** as the single home for the route + envelope + offline semantics, and cross-reference it from §3.2/§3.3/§3.9/§6.2. This keeps the diff readable and gives 315 one section to implement against.
- **Be explicit about the Noise carve-out** — this is the subtle, security-load-bearing part. The other channels are Noise-IK-wrapped; `0x04` is not, because the peer is GitHub-via-relay, not a paired device. The authenticity substitute is the HMAC. State plainly: the relay is a transparent forwarder of GitHub's already-signed payload; confidentiality of webhook contents over the relay hop is GitHub's TLS to the relay + the relay→Core Iroh transport's own QUIC encryption (the Iroh connection is encrypted at the QUIC layer even without the inner Noise), and integrity/authenticity is the Core-verified HMAC. Do not overstate ("end-to-end Noise") or understate ("relay sees plaintext it shouldn't") — be precise about the threat model.
- **Pin the encoding so 315 has no fork.** The whole point of 315.0 is to remove 315's design decisions. Choose the framing (length-prefixed fields vs CBOR map), the body ceiling, and the ack shape, and write them as MUST. A future reviewer cross-checks 315's wire bytes against this section.
- **Cross-platform note for 315** (carry it into the §3.4.1 text): the webhook route is plain TCP/HTTPS + an Iroh bidi — nothing `#[cfg(unix)]`; it builds on the Windows CI lane (Task 113), same as the WSS bridge.

## Handoff Notes (filled in when finishing)
- **Drift from plan** — None of substance. Two small framing choices made within the latitude the task explicitly granted ("pick one and pin it"): (1) the envelope encoding is the **length-prefixed framing** (big-endian `u32` length + bytes, in field order `delivery_id, signature_256, event_type, endpoint_id, body`), not CBOR — chosen because it matches the existing single-byte channel-tag/priming-write discipline in `crates/transport/src/channels.rs` and needs no serde dep on the relay's read/write path; (2) the ack is a **single status byte** with three defined values (`0x00`→200, `0x01`→4xx/400, `0x02`→5xx/500); any other byte or an early close = 5xx+drop+log. §3.3 was retitled "three logical channels" → "logical channels per pairing" (the list is now 3 device-originated + 1 relay-originated `0x04`); the three frozen `0x01`–`0x03` tags and their semantics are unchanged. Cited code symbols verified against `main`: `ChannelTag::{Api,PushHint,Pairing}` + `tag_from_byte` (channels.rs), `MAX_MESSAGE_SIZE = 64 MiB`, `MAX_ENDPOINT_ID_LEN`/`WSS_PATH_PREFIX`/`RelayState.wss_bridges`/`RelayMode::Custom` (relay api.rs/wss.rs).
- **Open questions for next task (315)** — (a) **Missing `X-Hub-Signature-256`**: pinned as a zero-length field that the Core MUST treat as an HMAC failure (`0x01`→400); confirm GitHub never legitimately omits it for a correctly-configured hook (it does not, but 315's parse should not panic on absence). (b) **`X-GitHub-Hook-ID` / other GitHub headers** are intentionally NOT in the five-field envelope — the Core routes on `event_type` + verifies on `body`; if 316/315 later needs the hook id, that is an additive envelope-field change re-locked in a new doc task, not silently added by 315. (c) The relay-side **per-request body-size cap** (25 MiB) must be enforced at the relay's HTTP layer too (reject oversized POSTs before dialing), independent of the Core's frame-level check — stated as the ceiling in §3.4.1; 315 enforces it on both ends.
- **Deliberate debt** — None. This is a finished spec with no placeholders; the `0x04` carve-out from the "relay sees ciphertext only" invariant (`design/11 §3.9`) is documented as a deliberate, bounded, HMAC-anchored exception (not debt). The relay-visibility carve-out is the security-load-bearing part and is stated precisely (relay sees body bytes in transit only; never the HMAC secret; no E2E Noise claim).
- **Smoke-gate state** — unchanged (doc-only task; `scripts/smoke.sh` and `scripts/smoke.d/*` untouched; no `crates/` files modified). `grep` verifications 1 + 2 clean; no markdownlint/link-check configured under `scripts/`, so the Tier-3 gate is the operator's read of the diff at the phase boundary.
