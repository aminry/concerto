# Prompt Template — Executing a Concerto Task

Hand this prompt to a fresh coding agent (Claude Code, Codex, Cursor agent, etc.) to execute one task from `tasks/`. The agent gets everything it needs from the task file plus the design docs the task references — no chat-history context required.

---

## How to use

1. Pick the next unstarted task file (lowest-numbered `tasks/NN-<slug>.md` whose work isn't yet committed).
2. Copy the template below, replacing `{TASK_PATH}` with the relative path to that task file (e.g., `tasks/06-proto-schema-scaffolding.md`).
3. Paste it as the first message to the agent.
4. Let the agent work. The agent's responsibilities are spelled out below; resist the urge to babysit.
5. When the agent reports done, **review the Handoff Notes section it added** to the task file. That's where any drift, open questions, or deliberate debt is recorded.
6. If the Handoff Notes flag drift that would affect a later task, edit that later task file *before* you start it — don't try to remember.

---

## The template (copy from the `---` markers)

---

You are executing **one** task from the Concerto V0.1 build. Concerto is a local-first orchestration platform for AI coding agents; the design is in `design/` and the build is decomposed into sequential tasks in `tasks/`.

**Your task file:** `{TASK_PATH}`

**Your job:** read the task file, read every input it points at, implement exactly what's in `Scope — in`, run every command in `Verification`, tick every box in `Definition of Done`, fill in `Handoff Notes`, and create the single commit specified at the bottom of the task file. Nothing more.

### Mandatory reading order (do this before writing any code)

1. **`tasks/README.md`** — the meta-document. Six decisions (D1–D6 in §3) constrain everything you do; the verification model in §5 is non-negotiable.
2. **Your task file** at `{TASK_PATH}` — top to bottom.
3. Every entry under your task's **`Inputs to read before starting`** section. This always includes:
   - The relevant design doc sections (`design/NN_*.md §X.Y`).
   - The **prior task's `Handoff Notes`** section. That's where the previous agent recorded any drift you need to know about. Treat it as load-bearing.
4. Skim `docs/interfaces/proto.md`, `docs/interfaces/schema.md`, `docs/interfaces/rust-api.md` so you know what public surface already exists. These files are auto-generated by `scripts/regen-interfaces.sh`; they're the canonical summary of what prior tasks locked in.

If any of those files don't exist yet (early Phase 0 tasks), don't invent them — the task file itself creates them.

### Rules of engagement

- **Stay inside `Scope — in`.** Anything in `Scope — out` is explicitly someone else's job. If you find a bug or smell outside your scope, note it in `Handoff Notes` under *Open questions for next task* — do not fix it.
- **Treat `Public interface this task locks` as a contract.** Once you commit, those types / proto messages / SQL columns / file paths are immutable until an explicit revision task changes them. Pick names carefully.
- **Run every verification command. Do not skip.** "It compiles" is not "it works." If a command fails, fix the root cause. Do not weaken the check (e.g., don't remove `-D warnings`, don't `#[allow(...)]` without justification, don't `--no-verify` past hooks).
- **Modify only files in `Outputs`.** If a file you didn't expect to touch needs to change, stop and add it to `Outputs` first — that's a meaningful signal that your understanding has drifted.
- **No `TODO` / `FIXME` / `unimplemented!()` / `todo!()` in new code** unless the task explicitly allows it as deferred work *and* you record it under *Deliberate debt* in `Handoff Notes` with the task number that will close it.
- **One commit per task.** Use the exact commit message at the bottom of the task file (you fill in the body if the template leaves gaps). Do not amend; do not split.
- **Don't push, don't open a PR, don't merge.** The operator handles git remote operations.
- **Don't modify prior tasks' files.** If you discover a prior task locked the wrong interface, note it in `Handoff Notes`; the operator will write a revision task.
- **Don't modify `design/`.** Design docs are the spec, not the workspace. Drift between code and design is captured in `Handoff Notes`.

### When you finish

1. Tick every checkbox in `Definition of Done` of the task file. If any one is false, you're not done — go fix it.
2. Fill in the `Handoff Notes` section *in the same file you just executed*. The four bullets must each have content (use `—` for "nothing to report" on the empty ones; do not delete the bullets). Concretely:
   - **Drift from plan:** anything you implemented differently than the task file said, and why. Be specific (function name, signature, reason).
   - **Open questions for next task:** anything the next task's executor should know that isn't already in the design doc.
   - **Deliberate debt:** any `TODO` you intentionally left, with rationale and the future task number that will close it.
   - **Smoke-gate state:** what the smoke gate now covers (e.g., "still v1; unchanged"; or "v2 active — covers X, Y, Z").
3. Stage the files in `Outputs`, plus this task file (with your filled-in Handoff Notes), and create a single commit with the message in the task file. If the message has a `<...>` placeholder, fill it before committing.
4. Report back with:
   - The commit SHA.
   - The smoke-gate state after your task.
   - Anything in `Handoff Notes` that the operator should pay attention to before starting the next task.

### When to stop and ask

Stop and ask the operator — do not improvise — if:

- The task file's `Inputs` reference a file that doesn't exist or a design-doc section that doesn't match what you find there.
- A verification command requires credentials or external services you don't have (e.g., real GitHub auth for Task 45).
- Two parts of the task file or two referenced design-doc sections contradict each other.
- You discover the prior task's `Handoff Notes` flag drift that would invalidate this task's `Public interface this task locks`.
- A `Scope — in` item is impossible to implement without changing something in `Scope — out`.

In all of those cases, write a one-paragraph summary of what you found and what you'd recommend; do not start coding around the ambiguity.

## After the agent reports done (operator checklist)

- Diff review is optional but cheap: `git show HEAD --stat` then spot-check one or two files. The Definition-of-Done checklist is the formal gate; this is a sanity check.
- **Read the Handoff Notes.** This is the only manual signal you can't get from CI. If anything in Drift / Open questions / Deliberate debt would affect the next task, edit that next task file *now*.
- Push the commit to the branch.
- Move on to the next task; do not parallelize unless the dependency graph in the task file explicitly allows it.

If a task fails verification and the agent can't recover, do **not** edit the prior commit. Either (a) make the task file more precise and rerun on a fresh checkout, or (b) split the task into two and renumber accordingly. The principle from `tasks/README.md` §7 holds: never edit shipped tasks' code outside of an explicit revision task.
